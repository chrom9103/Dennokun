# 試合生成（Control） 要件 — フェーズ分離

## 概要
- 試合生成は大きく2つの独立フェーズで構成する。UI上で両フェーズを分離して操作できるようにすることで、デバッグ性とユーザーの介入性を高める。

フェーズ構成:
- Phase1 — チームのタイムテーブル決定（Team timetable assignment）
- Phase2 — 審判/司会/タイマー等のスタッフ割当（Staff assignment）

---

## Phase1: チームのタイムテーブル決定

### 目的
- 対象チームを時間枠・会場に割り当て、`event_matches` の骨格（aff/neg チーム、時間枠、会場、順序）を作る。

### 入力
- 対象試合一覧（セクション・時間枠・会場の組み合わせ）
- 対象チーム一覧（`event_teams`）
- グループ制約（同グループ対戦禁止 等）
- シード関連制約（最大対戦回数）
- 試行回数パラメータ（`parameterTrialsMatchWrap` など）

### 出力
- 仮の `event_matches` レコード（チーム・時間枠・会場・順序が確定したが、スタッフ未割当の状態）をプレビュー用に生成。

### 検証ルール
- 同一チーム対戦禁止、再戦禁止、同グループ内対戦禁止、シード回数制限、肯定/否定バランス等をチェック。最終的に `checkSeedLimitAndThrowIfNeeded` 相当の検証を実施。

### 実装上の注意
- 大量試行は Web Worker 並列化で分散処理する。
- 成果物はまずフロント内の一時オブジェクトとして保持し、ユーザー承認後に永続化する。

---

## Phase2: スタッフ（審判/司会/タイマー等）の割当

### 目的
- Phase1 で確定した試合骨格に対し、審判や司会、タイマー等を割り当て、最終的に運用可能な `event_matches` レコードを完成させる。

### 入力
- Phase1 の生成結果（プレビューされた試合リスト）
- 判定者候補（`event_staffs`）
- 判定者の参加可能時間（`event_staff_present_timetable_segments`）
- 判定者の利害関係（`event_staff_interested_schools`, `event_staff_interested_teams`）
- 割当パラメータ（1試合あたりのジャッジ数、主審/副審優先等）

### 出力
- `event_matches` のスタッフ割当列が埋められた最終レコード（`main_judge_staff_id`, `sub_judge*_staff_id`, `timekeeper_staff_id` 等）

### 検証ルール
- スタッフの参加可能時間と試合時間が一致すること
- スタッフの利害関係（関係校/関係チーム）が当該試合と衝突しないこと
- 同一スタッフが同時刻に複数試合に割当てられていないこと

### 実装上の注意
- ジャッジ割当は競合解決を要するため、グリーディーとバックトラックを組み合わせたハイブリッド戦略を用いると現実的。
- Phase2 は Phase1 の出力に依存するため、Phase1 の再生成が必要になった場合は Phase2 割当の再計算をトリガーする。

### 部分確定・段階的割当の仕様（重要）
- 目的: 当日の現場運用に合わせ、試合ごとにスタッフ割当を段階的に確定できるようにする。
- 判定済みの試合: `event_matches.is_staffs_fixed = true` を立てることで、その試合のスタッフ割当はアルゴリズムから変更されない。
- 自動割当は「未割当かつ `is_staffs_fixed = false`」の試合のみ対象にする。既にデータの入っている割当は保持する。
- 運用例:
	- 事前: 第1試合だけを手動で確定し `is_staffs_fixed=true` にしておく。
	- 実運用: 第1試合の開始後に UI から「第2試合以降を自動割当」ボタンを押し、未割当分のみを割当。プレビュー後に確定保存。

### 手動操作と優先度
- UI上で個別試合カードを開き、手動でスタッフを割当／解除できる。手動で「確定」ボタンを押すと `is_staffs_fixed=true` となる。
- 手動割当は自動割当より優先される。自動割当は常に固定済み試合をスキップする。

### 自動割当の実行オプション
- 範囲指定: 全未割当 / 次のN試合 / 指定時間以降 のように範囲を限定できる。
- モード: プレビュー(一時割当をフロントで確認) → 承認 → 永続化 のステップを必須とする。

### 全体/個別生成ボタン（UI 要件）

- ボタン種別:
	- **全体生成**: ラベル例 `審判・司会タイマーを全試合生成`。動作は「該当イベントの全未割当試合（かつ `is_staffs_fixed = false`）を対象に自動割当を行い、プレビューを表示する」。
	- **個別生成（単一試合）**: 各試合カード上に `この試合のみ生成` ボタンを配置。動作は「その試合のみを対象に自動割当を行い、プレビューを表示する」。

- 共通 UI 挙動:
	- いずれのボタンもまずサーバー（またはローカル最適化エンジン）に対して「プレビュー生成」リクエストを送る。プレビューはフロントで表示し、ユーザーは差分を確認できる。
	- 永続化は別アクション（プレビュー画面の `確定` ボタン）で行う。永続化時に行ロックおよび再整合性チェックを実施する。
	- 自動割当は「既に手動で割当済みのフィールド（`main_judge_staff_id` 等）がある場合は上書きしない（既存値優先）」オプションを標準とする。完全上書きモードは管理者オプションとして提供しても良い。
	- 実行中は進捗インジケーター（全体パーセンテージ / 試合毎のステータス）を表示する。

- 実装上の注意点（補足）:
	- `個別生成` ボタンは UI 側で即時プレビューを返せるよう、サーバーに短時間のタイムボックスを設ける（レスポンス優先）。複雑な最適化はバックグラウンドジョブで実行し、結果を非同期で受け取るワークフローを用意してもよい。  
	- 部分確定の UX として、プレビュー画面に「この試合だけ確定する」「この範囲を確定する」など選択肢を用意する。


### 競合防止・整合性
- 割当ジョブは DB 行ロック（`SELECT ... FOR UPDATE`）または分散ロック（Redis lock）で対象試合をロックして並列実行の競合を防ぐ。
- 永続化時はトランザクション内で `is_staffs_fixed` と既存割当を再チェックし、競合があればロールバックして UI にエラーメッセージを返す。


---

## UI 操作フロー（推奨）
1. Phase1 パラメータを設定して「生成」→ プレビュー表示
2. 必要に応じて個別試合を手動調整（ドラッグ/編集）→ Phase1 確定
3. Phase2 パラメータを設定して「割当」→ スタッフ割当のプレビュー表示
4. 最終確認後、`event_matches` を DB に確定保存

## 関連DB（フェーズ別）
- Phase1: `event_sections`, `event_teams`, `event_team_groups`, `event_rooms`, `event_timetable_segments`, `event_matches`
- Phase2: `event_staffs`, `event_staff_present_timetable_segments`, `event_staff_interested_schools`, `event_staff_interested_teams`, `event_matches`

## 備考
- 生成は不可逆のため、DB 保存前のプレビュー確認を必須にする。
- スケール要件があれば、Phase1 は複数ワーカーで並列実行、Phase2 は割当の最適化エンジン（Python バックエンド）にオフロードすることを推奨。
