# Git 運用ルール

## 目的
チーム開発でのコンフリクト低減、レビュー効率化、履歴の可読性を担保するための Git 運用ルールを定義する。

## 共通ルール
- 常に `main`（または `master`）は保護ブランチとする。直接プッシュ禁止。
- すべての変更は Pull Request（PR）を通してマージする。
- PR は原則としてレビューを行うこと（担当チームから1名が望ましい）。
- 小さな修正（typo 等）は `docs`/`fix` で即時対応可だが、必ず PR を作成する。

## チームサブメインブランチ運用（ctrl / algo / infra）
- 各チームごとにサブメインブランチを設け、日常の統合ポイントとする:
  - `ctrl`  — 運営・管理チームのサブメインブランチ
  - `algo`  — アルゴリズム・基盤チームのサブメインブランチ
  - `infra` — インフラチームのサブメインブランチ

- 運用ルール:
  1. 開発者は必ず自チームのサブメインブランチから作業ブランチを切る（例: `chrom/ctrl/feat/...` は `ctrl` をベースに作成）。
  2. 個別作業は該当チームのサブメインブランチへ向けて PR を作成し、チーム内レビューを完了させる。
  3. サブメインブランチへのマージはチーム内の合意（最低1名レビュー）を前提とする。
  4. `main` ブランチへは**各サブメインブランチのみ**から PR を作成し、クロスチームレビューと QA を経てマージする。個人作業ブランチから直接 `main` へ PR を出さない。
  5. `main` へのマージはリリース担当者またはチームリードが行う。

- 理由:
  - チーム単位での安定した統合ポイントを作ることで、クロスチームのコンフリクトを低減し、責任範囲を明確にするため。

## ブランチ命名規則
パターン:
<作者名>/<チーム>/<Prefix>/<短い説明>

- `作者名`: git のユーザ名（例: `chrom`）
- `チーム`: `ctrl`, `algo`, `infra` などディレクトリ分担に合わせること
- `Prefix`（必須）:
  - `feat` : 新機能
  - `fix`  : バグ修正
  - `update`: 仕様修正/改善
  - `docs` : ドキュメント
- 短い説明: 英小文字とハイフン、最大 50 文字程度（例: `master-common-ui`）

例:
- `chrom/ctrl/feat/master-common-ui`
- `chrom/algo/fix/matching-performance`

注意:
- 他チームの領域を変更する場合はチーム名をそのチーム名にする（責任所在を明確にする）。

## コミットメッセージ規約
フォーマット:
<type>: <短い要約>

（空行）
<詳細な説明（任意）>

`type` は以下を使用:
- `add`   : ファイル追加
- `feat`  : 機能追加
- `fix`   : バグ修正
- `update`: 仕様変更 / 機能修正
- `docs`  : ドキュメント

ガイドライン:
- 1コミット = 1意図（粒度は小さめが望ましい）。
- 変更内容が複数ある場合は、コミットを分割することを推奨。
- コミットメッセージの要約は原則として日本語で記載する。

コミットメッセージ例:

feat: イベントチームのTSVインポート機能を追加

## PR タイトル/説明テンプレート
- タイトル: `<Prefix>: <要約>`（コミット規約と整合）
- 説明: 何をしたかを記載。
- 関連 Issue やスクリーンショットを添付する。

PR タイトル例:
feat: 試合編集画面に投票詳細入力機能を追加
試合編集画面で、各ジャッジの投票内容を入力できるようにしました。
- 審判最大5人分の投票詳細を管理
- 投票内容は `event_match_voting_details` テーブルに保存
/event/{event_id}/matches/{match_id}/edit で確認できます。
