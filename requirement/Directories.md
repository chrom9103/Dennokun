## 1. ディレクトリ構造とルーティング
Next.jsの **App Router** を採用し、チームごとの作業範囲を物理的なディレクトリで分離することで、マージコンフリクトを最小化します。

### プロジェクト全体の構成
```text
/
├── frontend/               # Next.js (Tailwind CSS)
│   ├── src/
│   │   ├── app/            # App Router (ページ定義)
│   │   ├── components/     # 共通コンポーネント (atoms, molecules)
│   │   └── lib/            # APIクライアント, ユーティリティ
├── backend/                # FastAPI (Python)
│   ├── app/
│   │   ├── api/            # エンドポイント定義
│   │   ├── core/           # ML最適化ロジック (最適化エンジン)
│   │   └── models/         # Pydanticモデル / SQLAlchemyモデル
├── infra/                  # k8sマニフェスト, Dockerfile
└── docker-compose.yml      # 開発環境用一括起動設定
```

### Webページ・ディレクトリ詳細
URL構造をそのままチームの担当範囲とします。

| パス (URL) | 担当チーム | 画面概要 |
| :--- | :--- | :--- |
| `/dashboard` | 共通 | 大会一覧、新規大会作成 |
| `/events/[id]/overview` | 共通 | 大会概要、基本設定 |
| `/events/[id]/master/*` | **運営・管理** | 学校、チーム、スタッフ、時間枠のCRUD (TSV) |
| `/events/[id]/matches/control` | **基盤・アルゴ** | **【最重要】** マッチング生成実行・微調整UI |
| `/events/[id]/matches/board` | **基盤・アルゴ** | 大会全体の進行ボード (タイムテーブル形式) |
| `/events/[id]/matches/[mid]/edit`| **運営・管理** | 試合結果（勝敗・スコア・ジャッジ投票）入力 |
| `/events/[id]/reports/*` | **運営・管理** | 予選・本選順位表、集計結果表示 |

## 2. チーム役割とミッションの詳細

### A. 運営・管理チーム（4名）(りく/ひかる/隼介/なつ)
ミッション: **「データの整合性と、現場の使いやすさを保証する」**
*   **マスタ管理ロジック:** 複雑なTSVのバリデーション、および `event_schools` 等のマスタ系API/UIの実装。
*   **集計エンジンの開発:** 試合結果（`event_matches`）からリアルタイムで順位を算出するロジックの実装。
*   **デザインの一貫性:** Tailwind CSSを用い、全ページで共通の操作感（ボタン、モーダル等）を徹底する。

### B. アルゴリズム・基盤チーム（4名）(そら/やすほ)
ミッション: **「Python MLの力で、大会運営の『知能』を創る」**
*   **最適化エンジンの移植:** PythonのMLライブラリ（`PuLP`, `scipy.optimize`等）を用い、利害関係を回避しつつ最適な対戦・ジャッジ割り当てを行う。
*   **インタラクティブ調整UI:** 自動生成された結果を、ドラッグ＆ドロップや反転スイッチで「人間が最終調整」できる高度な画面の開発。
*   **非同期処理の管理:** 重い生成処理をバックグラウンドで走らせ、進行状況をフロントに伝える仕組み。

### C. インフラ担当（1名）
ミッション: **「開発からデプロイまでを、ノンストップにする」**
*   **開発環境の整備:** `docker-compose up` でPostgreSQL、Frontend、Backendが完全にリンクした環境を提供。
*   **本番環境の構築:** Kubernetes (k8s) マニフェストを作成し、リソース制限やオートスケーリングを設定。
*   **DBマイグレーション:** `Alembic` 等を用いたDB定義のバージョン管理。

## 3. 実際の開発の進め方

### ① スキーマ駆動開発フロー
1.  **FastAPI** 側でPydanticを用いてリクエスト・レスポンスの型を定義。
2.  `/openapi.json` から **OpenAPI Generator** を通じてフロントエンドのAPIクライアントを自動生成。
3.  **Frontend** はその型をインポートして開発。これにより、通信部分のバグを事前に封じ込めます。
4.  APIの定義書は`requirements/plan/openapi.yaml`に配置しましょう。

### ② ローカル開発手順 (Docker Compose)
メンバーは以下の手順で開発を開始します。
```bash
docker compose build
docker-compose up

# ブラウザでアクセス
# Frontend: http://localhost:3000
# API Docs: http://localhost:8000/docs
```

### ③ Git運用とコミュニケーション
*   **ブランチ戦略:** チームごとに主のブランチを分ける。  
    * 運営・管理チーム: `ctrl`
    * アルゴリズム・基盤チーム: `algo`
    * インフラチーム: `infra`
    そこから自分が作業するブランチを切る。  
      
    例: chrom/ctrl/feat/master-common  
    **{名前}/{チーム(担当範囲)}/{Prefix}/{作業箇所}**の形で記載する。  
    * 名前は、gitの名前など個人がわかるものを統一して使うこと
    * チームは、`ctrl/algo/infra`のいずれかになるはずである。自分が属するチームと違うチームの作業を行う場合は、その別のチームの名称とする。(インフラメインだけどアルゴリズムを修正する...とか)
    * Prefixは次の3種類とする
        * `feat`  : 機能の追加
        * `fix`   : バグ(問題)の修正
        * `update`: 機能の修正

*   **コミットメセージ:** 必ず記載してコミットする。  
    例: feat: `events`テーブルのCRUD操作用のAPIを定義  
    **{Prefix}: {作業内容}**の形で記載する。  
    * Prefixは次の5種類とする
        * `add`   : ファイルの追加
        * `feat`  : 機能の追加
        * `fix`   : バグ(問題)の修正
        * `update`: 機能の修正
        * `docs`  : ドキュメントの書き込み

*   **決定事項の記録:** 「なぜPostgreSQLのこの型にしたか」「なぜこのMLライブラリにしたか」等は `requirement/plan` 内にMarkdownで保存。
